## `struct Decoder`

A decoder is a value that turns a `JsonValue` into a `T`, or says
why it cannot -- carrying the PATH it is currently looking at so a
failure names the field rather than the document.

## `let int (): Decoder[Int]`

JSON has one number type, so an `Int` decoder has to decide what to
do with `41.5`. It REFUSES rather than truncating: a fractional value
where a count was expected is a disagreement about the document, and
silently producing 41 hides it until something downstream is wrong
for a reason nobody can trace back to here.

## `let field (key: String) (inner: Decoder[T]): Decoder[T]`

Requires the key to be present. Its absence is a different failure
from its value being the wrong shape, and says so.

## `let optional_field (key: String) (inner: Decoder[T]): Decoder[Option[T]]`

Absent or null both give `None`, which is what an optional field in
a real API means. `field(k, nullable(d))` is the other reading --
the key must be there, and its value may be null -- and both
spellings exist because both situations do.

## `let at (keys: Array[String]) (inner: Decoder[T]): Decoder[T]`

A LIST of keys rather than a dotted string: a key containing a dot
is ordinary JSON, and a path syntax would have to invent an escape
for it. It is also nothing but nested `field`s, which is why the
path in an error comes out right without this function knowing
anything about paths.

## `let fail (msg: String): Decoder[T]`

A user-written failure gets the same ` at <path>` treatment as a
built-in one, so the message should be a clause and not a sentence.

## `let and_then (a: Decoder[A]) (f: (A) -> Decoder[T]): Decoder[T]`

Runs a decoder chosen by what the first one produced -- a version
field deciding how to read the rest of the payload, which no amount
of `mapN` can express.

## `let one_of (options: Array[Decoder[T]]): Decoder[T]`

The first alternative that succeeds. The individual failures are
DISCARDED: `one_of` is used where several shapes are equally
acceptable, and a caller told that the value was neither a String
nor a Number learns more from that than from both attempts quoted
back at them.

## `let decode_string (d: Decoder[T]) (text: String): Result[T, String]`

Parses and decodes in one step. A parse error arrives phrased by
`json_parse` and unchanged, so a caller has ONE error path rather
than two -- which is the difference between `match` and nested
`match`.
